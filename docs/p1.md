# 1. Project invariants

The system synchronizes Jiandaoyun form records into a Feishu Bitable table.

The Feishu table contains two categories of fields:

- **Managed fields:** explicitly authorized for synchronization from Jiandaoyun.
- **Protected fields:** maintained manually in Feishu or by other Feishu workflows.

The following rules are mandatory:

1. Jiandaoyun is the source of truth only for managed fields.
2. Protected fields must never be modified by the synchronization service.
3. All Feishu fields are protected by default.
4. Identical field names do not imply permission to synchronize.
5. Every managed field must be explicitly approved in configuration.
6. Record identity is based on Jiandaoyun `_id`.
7. Jiandaoyun deletion must never cause physical deletion of a Feishu record.
8. Every future write operation must pass through a centralized field ownership validator.
9. New Feishu fields must remain protected unless explicitly configured otherwise.
10. P1 must perform no real Feishu writes.

These invariants take priority over convenience or automatic field matching.

# 3. P1-A — Feishu API integration

## 3.1 Authentication

Use a Feishu enterprise self-built application.

Required credentials:

```dotenv
FEISHU_APP_ID=
FEISHU_APP_SECRET=
FEISHU_APP_TOKEN=
FEISHU_TABLE_ID=
```

`FEISHU_APP_ID` and `FEISHU_APP_SECRET` identify the Feishu application.

`FEISHU_APP_TOKEN` identifies the Bitable app.

`FEISHU_TABLE_ID` identifies the specific table.

These identifiers have different purposes and must not be confused.

Use the official Feishu Open Platform authentication mechanism to obtain `tenant_access_token`.

Authentication endpoint:

```text
POST https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal
```

Request:

```json
{
  "app_id": "<FEISHU_APP_ID>",
  "app_secret": "<FEISHU_APP_SECRET>"
}
```

Expected successful response includes:

```json
{
  "code": 0,
  "tenant_access_token": "...",
  "expire": 7200
}
```

The response is illustrative; validate the actual response against official documentation.

Requirements:

- Cache access tokens in memory.
- Refresh tokens before expiration.
- Do not request a new token for every API call.
- Never log App Secret or access tokens.
- Handle authentication failures explicitly.
- Do not persist access tokens in Git-tracked files.
- Support concurrent callers without unnecessary duplicate refresh requests.

Create:


Suggested interface:


Use the official Feishu Bitable v1 APIs.

Relevant endpoints include:

```text
GET /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}

GET /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/fields

GET /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records
```

Before implementation, verify exact endpoint paths, HTTP methods, pagination parameters, and response structures against official documentation.

Do not assume all endpoints return the same response envelope.

Do not implement write methods in P1.

## 3.3 Permission validation

Implement a read-only permission check.

The application must have the necessary Bitable read permissions and actual access to the target Bitable resource.

Permission scopes alone may not guarantee resource access.

The CLI must distinguish:

- Invalid credentials.
- Missing API permissions.
- Missing resource authorization.
- Invalid app token.
- Invalid table ID.
- Network failures.
- Rate limiting.

Provide actionable error messages without exposing credentials.

## 3.4 Feishu pagination

Implement complete record pagination.

Requirements:

- Use Feishu's documented `page_token` mechanism.
- Respect API page-size limits.
- Continue until the documented end-of-pagination condition.
- Detect repeated page tokens.
- Detect duplicate record IDs.
- Treat malformed responses as errors.
- Never silently return incomplete data.
- Handle empty tables correctly.

For P1, records are read-only.

# 4. P1-B — Field discovery and mapping

## 4.1 Jiandaoyun metadata

Reuse the P0 Jiandaoyun client.

Jiandaoyun widget metadata has already been verified:

```json
{
  "name": "_widget_1730273046580",
  "widgetName": "_widget_1730273046580",
  "label": "PI Code",
  "type": "text"
}
```

Use:

- `name` as stable source field ID.
- `label` as source display name.
- `type` as source field type.

Do not use `widgetName` as the display label.

## 4.2 Feishu metadata

Retrieve field definitions from Feishu.

Retain:

- Field ID.
- Field name.
- Field type.
- Field properties where relevant.

Use Feishu's stable field ID as the target identity in mapping configuration.

Do not use field names as the only persistent identifier.

## 4.3 Candidate matching

Create a field discovery service:

```text
src/jdy_feishu_sync/services/field_discovery.py
```

It should compare Jiandaoyun and Feishu field metadata.

Generate candidates based on exact normalized display-name matches.

Allowed normalization:

- Unicode normalization.
- Trimming leading and trailing whitespace.

Do not automatically match unrelated names using fuzzy matching.

Do not automatically enable candidates.

For each candidate, report:

- Jiandaoyun field ID.
- Jiandaoyun label.
- Jiandaoyun type.
- Feishu field ID.
- Feishu field name.
- Feishu type.
- Type compatibility assessment.
- Suggested status.

Suggested statuses:

- `candidate`
- `incompatible`
- `ambiguous`
- `manual_review`

Type compatibility should be conservative.

For example:

| Jiandaoyun | Feishu | Initial assessment |
|---|---|---|
| text | Text | Compatible candidate |
| textarea | Text | Compatible candidate |
| datetime | Date | Conversion required |
| radiogroup | Single Select | Option validation required |
| combo | Single Select | Manual review |
| user | Person | Manual review |
| upload | Attachment | Unsupported in P1 |
| subform | Any | Unsupported in P1 |

These are preliminary compatibility rules, not authorization to synchronize.

Actual type codes and field properties must be obtained from Feishu metadata.

# 5. P1-C — Field ownership

## 5.1 Approved mapping configuration

Create a separate configuration file:

```text
config/field_mapping.yaml
```

This file contains only explicitly approved managed mappings.

Example:

```yaml
version: 1

identity:
  source_record_id: _id
  target_record_id_field: jdy_id

managed_fields:
  - source_id: "_widget_1730273046580"
    target_id: "fld_example"
    transform: text
```

This example must not be treated as an approved production mapping.

If no mapping has been approved, the configuration should contain:

```yaml
version: 1

identity:
  source_record_id: _id
  target_record_id_field: jdy_id

managed_fields: []
```

An empty mapping is valid and means no business fields are authorized for synchronization.

## 5.2 Reserved system fields

Reserve the following Feishu fields for future synchronization bookkeeping:

- `jdy_id`
- `jdy_deleted`
- `jdy_updated_at`
- `synced_at`

Do not create these fields automatically in P1.

Do not assume they already exist.

Their final field IDs and types must be validated before P2.

Treat these fields as system-managed only after explicit configuration and validation.

Do not allow business-field mappings to target reserved system fields.

## 5.3 Ownership validator

Create:

```text
src/jdy_feishu_sync/services/field_ownership.py
```

Suggested interface:

```python
class FieldOwnershipPolicy:
    def validate_mapping(self, mapping, source_fields, target_fields):
        ...

    def build_update_fields(self, source_record: dict) -> dict:
        ...
```

Requirements:

- Only configured managed fields can appear in update payloads.
- Unknown source fields are ignored.
- Unknown target fields cause validation failure.
- Duplicate source mappings are rejected.
- Duplicate target mappings are rejected.
- Incompatible types are rejected unless an explicitly supported transform exists.
- Unsupported transforms are rejected.
- Disabled mappings are ignored.
- Protected fields never appear in generated update payloads.
- Reserved fields cannot be targeted by business mappings.
- Missing source fields must not silently become null values.
- Explicit source null values must follow a documented transformation policy.
- Field mapping must fail closed.

Use stable target field IDs for authorization.

If the Feishu API requires field names in write payloads, resolve IDs to current field names only after validating the IDs against live metadata.

Never authorize writes solely by matching field names.

## 5.4 Safe payload construction

Implement pure functions for building proposed Feishu update payloads.

These functions must not make HTTP requests.

Example:

```python
source_record = {
    "_id": "source-001",
    "_widget_1730273046580": {
        "value": "PLA"
    },
}

payload = policy.build_update_fields(source_record)
```

The exact Jiandaoyun field value structure must be inspected and normalized according to the real API schema. Do not assume all widget values are plain strings or have a `value` property.

The resulting payload must contain only authorized managed fields.

Do not include target-only fields.

Do not merge existing Feishu records into update payloads.

Do not construct whole-record replacement payloads.

## 5.5 Safety preview

Implement:

```bash
jdy-sync preview-update --record-id <JDY_RECORD_ID>
```

This command should:

1. Read the Jiandaoyun record using the supported P0 client or a verified read-only lookup method.
2. Load the approved mapping.
3. Validate the mapping against live metadata.
4. Build the proposed update payload.
5. Display the field names that would be updated.
6. Show that protected fields are excluded.
7. Make no Feishu write requests.

Do not display sensitive field values by default.

If the P0 client does not yet support single-record lookup, either implement a verified read-only lookup or use an existing complete read path. Do not invent an API endpoint.
