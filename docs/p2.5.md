# P2.5 — Intelligent Schema Mapping and Provisioning

## Background

The project `jdy-feishu-sync` synchronizes Jiandaoyun records to Feishu Bitable.

Currently, configuring synchronization requires manually creating Feishu columns, retrieving field IDs, and editing `config/field_mapping.yaml`.

Implement a safe schema-assistance workflow that generates mapping proposals, creates approved missing columns, and produces a validated mapping automatically.

This feature must preserve the existing field ownership and synchronization safety guarantees.

## Goals

1. Automatically discover JDY and Feishu field schemas.
2. Generate intelligent mapping proposals.
3. Reuse compatible existing Feishu columns when explicitly approved.
4. Create missing Feishu columns after explicit approval.
5. Automatically retrieve the created Feishu field IDs.
6. Generate the final `field_mapping.yaml`.
7. Integrate with the existing Preflight Validation pipeline.

## 1. Schema discovery

Read:

- JDY widget IDs, labels, types and relevant properties.
- Current Feishu field IDs, names, types and properties.
- A representative or complete read-only sample of JDY record values for type validation.

Do not modify either system during discovery.

## 2. Mapping proposal engine

For each JDY field, generate one of:

- MATCH_EXISTING
- CREATE_NEW
- UNSUPPORTED
- AMBIGUOUS
- IGNORE

Use deterministic rules:

- Exact normalized name match.
- Compatible field types.
- Unique target matching.
- Known source-to-target transforms.
- Explicit conflict detection.

Use confidence levels HIGH, MEDIUM and LOW.

Do not silently authorize any proposal.

Never use fuzzy name similarity as sufficient authorization to write an existing field.

## 3. Proposal format

Generate:

`config/field_mapping.proposed.yaml`

Each proposal must contain:

- Source field ID.
- Source label.
- Source type.
- Proposed action.
- Proposed target name.
- Existing target field ID, if applicable.
- Proposed target type.
- Transform.
- Confidence.
- Explanation.
- Approval status, default false.

Unsupported and ambiguous fields must include actionable explanations.

## 4. CLI

Add:

`jdy-sync schema-propose --output config/field_mapping.proposed.yaml`

`jdy-sync schema-review --proposal config/field_mapping.proposed.yaml`

`jdy-sync schema-apply --proposal config/field_mapping.proposed.yaml --confirm-schema-write`

`schema-propose` and `schema-review` must be read-only.

`schema-apply` may create only explicitly approved missing fields.

It must never create or modify business records.

## 5. Safe schema provisioning

Before creating any field:

1. Validate target app token and table ID.
2. Re-read live Feishu schema.
3. Check whether the field already exists.
4. Reject ambiguous or incompatible existing fields.
5. Reject name collisions.
6. Verify the field type is supported.
7. Verify explicit approval.
8. Create only missing approved fields.
9. Retrieve and persist the real returned field ID.
10. Re-read schema to confirm the result.

Never rename, delete or change the type of an existing Feishu field.

If field creation succeeds but the process crashes before recording its ID, recovery must discover and reconcile the existing field instead of blindly creating another one.

## 6. Generate final mapping

Generate `config/field_mapping.yaml` using actual verified Feishu field IDs.

Preserve the existing mapping structure:

- identity
- system_fields
- managed_fields

Never replace previously approved mappings without an explicit reviewed change.

Do not include unapproved proposals.

Do not infer authorization from field names alone.

## 7. System fields

Handle `jdy_id` and `jdy_deleted` separately from business fields.

Ensure their expected Feishu types:

- `jdy_id`: Text
- `jdy_deleted`: Checkbox

Reuse existing fields only after validating their types and identities.

Do not create duplicate system fields.

## 8. Type support

Initially support only types with verified conversion and Feishu API behavior:

- Text
- Number
- Date
- Checkbox
- Single-select
- Multi-select

Mark unsupported JDY widget types explicitly.

For dates, use the existing strict timestamp conversion and timezone policy.

Do not create read-only Feishu system fields as synchronization targets.

## 9. Safety

- JDY remains authoritative only for explicitly approved fields.
- Existing unapproved Feishu fields remain protected.
- Never perform whole-record replacement.
- Never physically delete Feishu records.
- Never auto-approve proposed mappings.
- Never run record synchronization as a side effect of schema provisioning.
- Never modify the SQLite execution journal during schema discovery.

## 10. Tests

Add tests for:

- Exact name and compatible type.
- Similar name but ambiguous target.
- Same name but incompatible type.
- Multiple matching target fields.
- Missing target field.
- Unsupported widget type.
- Unapproved proposal.
- Approved CREATE_NEW.
- Approved MATCH_EXISTING.
- Duplicate schema-apply execution.
- Interrupted field creation recovery.
- Existing mapping preservation.
- Field ownership protection.
- Final mapping with real field IDs.
- Preflight compatibility.

Run all P0/P1/P2 regression tests.

## Acceptance

1. A fresh target table can be configured without manually creating every business column.
2. The proposal lists all JDY fields and explains the suggested mapping.
3. No schema writes occur before explicit approval.
4. Approved missing columns are created automatically.
5. Created field IDs are retrieved automatically.
6. The final mapping passes `validate-field-mapping`.
7. Record synchronization is not triggered.
8. No existing Feishu data or protected field is modified.

Stop after implementation and tests. Do not execute production schema changes automatically.
