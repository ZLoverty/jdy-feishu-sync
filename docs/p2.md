# Agent Instruction — P2 Safe Initial Synchronization

## 0. Context

Project: `jdy-feishu-sync`

Completed phases:

- P0: Jiandaoyun read-only integration
- P1: Feishu read-only integration, field discovery, ownership configuration and safe payload preview

Current phase: **P2 — Safe Initial Synchronization**

Continue development in the existing repository. Preserve all P0/P1 behavior and tests.

P2 introduces controlled Feishu writes for the first time.

Do not implement Webhooks, background polling, reconciliation scheduling or production deployment. Those belong to P3–P5.

---

# 1. Core invariants

These requirements are non-negotiable.

1. Jiandaoyun is authoritative only for explicitly approved managed fields.
2. Every other Feishu field is protected.
3. Existing Feishu records must never be replaced wholesale.
4. Updates must contain only approved managed fields and authorized system fields.
5. Never physically delete Feishu records.
6. Every Jiandaoyun `_id` must correspond to at most one Feishu record.
7. Network retries must not silently create duplicates.
8. Ambiguous existing-record matches must block writes.
9. An incomplete source read must never be treated as a complete snapshot.
10. Dry-run is the default behavior.
11. Production writes require explicit operator authorization.
12. All mutation operations must be auditable.

Field ownership rules must be enforced in code, not merely documented.

# 3. System field schema

P2 uses the following Feishu fields:

| Field | Type | Purpose |
|---|---|---|
| `jdy_id` | Text | Stable Jiandaoyun record ID |
| `jdy_deleted` | Checkbox | Soft deletion status |
| `jdy_updated_at` | Date or compatible timestamp representation | Source update time |
| `synced_at` | Date or compatible timestamp representation | Last successful synchronization |

Use the actual Feishu field IDs in configuration.

Do not assume field names uniquely identify fields.

## 3.1 Configuration

Extend the approved mapping:

```yaml
version: 1

identity:
  source_record_id: _id
  target_record_id_field: jdy_id

system_fields:
  jdy_id:
    target_id: "fld_actual_id"
  jdy_deleted:
    target_id: "fld_actual_deleted"
  jdy_updated_at:
    target_id: "fld_actual_updated"
  synced_at:
    target_id: "fld_actual_synced"

managed_fields:
  - source_id: "_widget_1730273046580"
    target_id: "fld_actual_pi_code"
    transform: text
```

All example IDs must be replaced by real IDs discovered through the Feishu API.

## 3.2 Validation

Before any write:

- Validate every configured target field ID.
- Validate actual field types.
- Reject duplicate target IDs.
- Reject business mappings that target system fields.
- Reject invalid or unsupported transforms.
- Reject missing identity field.
- Reject a configuration referencing a deleted field.
- Ensure `jdy_id` is writable and stores an exact source ID.
- Validate timestamp conversion against the target field type.

Missing or incompatible required system fields must block execution.

Do not automatically create or alter fields.

A CLI command should explain the required schema and report missing fields.

# 4. Record identity and legacy data

## 4.1 Primary identity

Use:

```text
Jiandaoyun record _id ↔ Feishu jdy_id
```

A matching Feishu record is found only when its `jdy_id` exactly equals the Jiandaoyun `_id`.

Do not use PI Code, material name, row number, or other business fields as an implicit primary key.

## 4.2 Existing Feishu records

Build an index of all Feishu records by `jdy_id`.

Classify records into:

- Valid identity: exactly one Feishu record per nonempty `jdy_id`.
- Legacy unlinked: `jdy_id` is empty.
- Duplicate identity: multiple Feishu records share one nonempty `jdy_id`.
- Invalid identity: malformed or non-string identity values.

Duplicate or invalid identities must block write execution.

## 4.3 Legacy record matching

Do not automatically assign Jiandaoyun IDs to legacy Feishu records using matching business-field values.

Implement an explicit adoption workflow.

Suggested file:

```csv
jdy_id,feishu_record_id
source_record_id,rec_existing_record_id
```

Command:

```bash
jdy-sync validate-adoption --file config/adoption.csv
```

Validation must ensure:

- Both records exist.
- Every source ID is unique.
- Every Feishu record ID is unique.
- The target row has no conflicting `jdy_id`.
- The target is not already claimed by another source.
- No ambiguous matches remain in the adoption file.

The adoption file is a manually reviewed authorization, not an automatically generated match.

During execution, adoption should bind the identity and update only approved fields.

If there are legacy unlinked records and unmatched source records, default to blocking automatic creation until the operator explicitly chooses how to handle them.

A reviewed adoption file, or explicit authorization to create new rows despite unmatched legacy records, is required.

# 5. Snapshot acquisition

Reuse P0 and P1 clients.

Read:

1. All Jiandaoyun records.
2. All Feishu records.
3. Current field metadata.
4. Approved field mapping.

## 5.1 Completeness requirements

A snapshot is valid only when:

- Every API page is retrieved successfully.
- Pagination terminates normally.
- No duplicate source IDs are detected.
- No duplicate Feishu record IDs are detected.
- All required metadata is available.
- Required source fields can be interpreted safely.

Any incomplete read must abort planning.

Do not convert API errors into empty lists.

## 5.2 Snapshot model

Create a structured representation containing:

- Snapshot creation time.
- Source record count.
- Target record count.
- Mapping configuration fingerprint.
- Source identity set.
- Target identity set.
- Data required for planning.

Keep snapshots in memory by default.

Do not store raw business data in logs.

# 6. Deterministic synchronization planner

Create:

```text
src/jdy_feishu_sync/services/sync_planner.py
```

Suggested interface:

```python
class SyncPlanner:
    def build_plan(
        self,
        source_records,
        target_records,
        mapping,
        adoption,
    ):
        ...
```

The planner must be pure and perform no HTTP requests.

## 6.1 Supported actions

| Action | Meaning |
|---|---|
| CREATE | Source exists; no linked Feishu record |
| UPDATE | Linked record exists; managed fields differ |
| ADOPT | Explicitly approved legacy record linkage |
| SKIP | Linked record already matches |
| BLOCK | Unsafe or ambiguous operation |

Do not introduce DELETE actions in P2.

## 6.2 Field-level diff

Compare only managed fields and relevant system fields.

Ignore differences in protected fields.

A protected-field difference must never trigger an update.

For example:

```text
Source:
  PI Code = PLA01

Target:
  PI Code = PLA00
  Internal Notes = "Approved by team"
```

The update must modify only PI Code and authorized system fields.

`Internal Notes` must remain untouched.

## 6.3 Missing and null values

Define separate semantics for:

- Source field absent.
- Source field explicitly null.
- Source field empty string.
- Source field empty array.
- Unsupported source value.

Rules:

- Absent fields must not automatically clear target values.
- Explicit null handling must be defined by the approved transform.
- Unsupported values must block that operation.
- No implicit conversion to an empty string.
- No silent loss of attachments or nested data.

## 6.4 Deterministic plan

The same snapshots and mapping must produce the same plan.

Use stable ordering by source record ID.

Generate a plan fingerprint based on canonicalized operation content, mapping fingerprint and relevant snapshot state.

Avoid including nondeterministic timestamps in the plan fingerprint.

# 8. Feishu write adapter

Extend the Feishu adapter with documented Bitable v1 record creation and update endpoints.

Verify the exact official API paths, request formats, field-name requirements, response codes and limits before implementation.

Do not guess API behavior.

Suggested methods:

```python
class FeishuClient:
    def create_record(self, fields: dict) -> dict:
        ...

    def update_record(
        self,
        record_id: str,
        fields: dict,
    ) -> dict:
        ...
```

## 8.1 Update behavior

Use field-level update requests.

Never send the complete existing Feishu record as an update.

Every update payload must be constructed through the approved ownership policy.

If the API requires field names rather than IDs:

1. Authorize by stable field ID.
2. Resolve the current name from live metadata.
3. Reject missing or ambiguous metadata.
4. Build the request using only the authorized resolved fields.

## 8.2 Create behavior

New records may include:

- `jdy_id`
- `jdy_deleted = false`
- Approved managed fields
- Other explicitly authorized system metadata

Do not populate protected fields.

## 8.3 Post-write bookkeeping

Do not update `synced_at` before the corresponding business-field operation succeeds.

Avoid treating a successful bookkeeping update as proof that the intended business-field update was applied.

A failed bookkeeping operation must remain visible as an incomplete synchronization outcome.

# 9. Safe execution

Implement:

```bash
jdy-sync sync-apply --plan reports/p2-plan.json
```

Applying a plan must require an explicit authorization flag:

```bash
jdy-sync sync-apply \
  --plan reports/p2-plan.json \
  --confirm-write
```

Without `--confirm-write`, the command must refuse to write.

## 9.1 Preflight checks

Before writing:

- Reload and validate mapping.
- Confirm plan fingerprint.
- Confirm current table and source configuration.
- Recheck source and target state relevant to planned operations.
- Detect stale plans.
- Reject unexpected target changes affecting managed fields.
- Reject duplicate identities.
- Reject new blocking conditions.
- Verify API write permissions.

The safest initial implementation may rebuild the plan immediately before execution and require it to match the approved plan.

Never execute a stale plan blindly.

## 9.2 Batching

Support:

```bash
jdy-sync sync-apply \
  --plan reports/p2-plan.json \
  --confirm-write \
  --batch-size 10
```

Requirements:

- Bounded batch size.
- Conservative concurrency; sequential writes are acceptable for fewer than 1,000 records.
- Rate-limit handling.
- Clear progress reporting.
- Ability to stop safely.
- Per-operation results.
- No whole-table rollback assumption.

## 9.3 Retry behavior

Differentiate:

- Definite success.
- Definite failure.
- Uncertain outcome.

For a CREATE request that times out after being sent, the record may already exist in Feishu.

Do not blindly retry CREATE.

Instead:

1. Query the target records.
2. Search for the exact `jdy_id`.
3. If exactly one exists, treat it as the created record and verify its fields.
4. If multiple exist, block.
5. If none exists, do not assume the first request definitely failed; apply a bounded verification/retry policy.
6. If the outcome remains uncertain, stop and require operator intervention rather than risking duplication.

For UPDATE, verify the target state before retrying.

Do not assume the Feishu create endpoint provides an idempotency key unless officially documented and verified.

## 9.4 Concurrent execution protection

P2 must prevent two local synchronization processes from writing concurrently.

Use a local execution lock.

The lock does not protect against independent workers on different machines. Document that limitation.

Do not claim distributed exactly-once semantics.

# 10. Execution journal

Create a durable local execution journal.

SQLite is acceptable and preferred.

Record:

- Plan ID.
- Operation ID.
- Source record ID.
- Target record ID, if known.
- Action.
- Attempt count.
- Execution state.
- Error category.
- Start and completion timestamps.

Suggested states:

```text
PENDING
IN_PROGRESS
SUCCEEDED
FAILED
UNCERTAIN
BLOCKED
```

Requirements:

- Journal writes must occur before external mutations.
- Restart must not silently forget incomplete operations.
- `IN_PROGRESS` after a crash must be treated as an uncertain outcome until reconciled.
- Successful operations must not be repeated unnecessarily.
- Journal must not contain API credentials.
- Avoid storing raw business data unless strictly necessary.

This journal is for P2 controlled execution. Do not implement the P3 Webhook queue yet.


- Read all source and target records.
- Match by `jdy_id`.
- Detect duplicate identities.
- Compare approved managed fields.
- Report mismatches.
- Report missing linked records.
- Report unresolved execution journal entries.

Do not modify data during verification.

## 11.1 Idempotence acceptance

After a successful initial synchronization:

```bash
jdy-sync sync-plan
```

must produce:

```text
CREATE: 0
UPDATE: 0
ADOPT:  0
BLOCK:  0
```

`SKIP` should account for all linked source records.

To achieve this, do not make volatile fields such as `synced_at` trigger repeated updates.

# 15. Acceptance procedure

P2 acceptance must use an isolated Feishu test table before any production write.

## Stage A — Automated tests

Run the full test suite.

All P0/P1/P2 tests must pass.

## Stage B — Read-only production planning

Generate a plan against the intended target table.

Review:

- Record counts.
- Managed-field mappings.
- Protected fields.
- Legacy unmatched records.
- BLOCK operations.

Do not write to production.

## Stage C — Isolated test table

Create a small test dataset containing:

1. A new source record.
2. An existing linked record.
3. A legacy unlinked record.
4. A Feishu-only manually maintained field.
5. A record requiring an update.

Test CREATE, UPDATE and ADOPT.

Confirm that protected values are unchanged.

## Stage D — Idempotence

Execute synchronization twice.

The second execution must perform no business-field writes.

## Stage E — Failure recovery

Simulate:

- Timeout after successful remote creation.
- Interrupted execution.
- Partial batch failure.

Verify that recovery does not silently create duplicates.

## Stage F — Production readiness

Produce a final production plan and verification report.

Do not execute production writes automatically as part of P2 acceptance.

Production execution requires a separate explicit operator decision.
